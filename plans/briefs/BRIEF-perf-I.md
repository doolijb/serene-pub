## The ruling (owner, 2026-11-13)

Lane key is **per connection, per host**: the `(scheme, host, port)` of the connection's resolved base URL. Width
(calls in flight at once): **1** for every local or managed host, **4** for a known cloud host. The width is a
constant (`CLOUD_LANE_WIDTH = 4` or the §24-checked name you choose), **not a setting**, and no admin UI is added.
The owner's words: "Per connection, per host. Need to safely tie it into the server management admin" — so the key
and width are computed in one place with one function the managed-server record can later feed (a width field on the
managed server), and the report says exactly where that hook is. Nothing is built for that later field.

## Challenger findings (2026-11-13) — read before anything else

- **[C7] The lane is released before a streamed request is sent.** `dispatch.ts:1450` has
  `execute: () => adapter.generateText()`; every streaming adapter returns a lazy `completionResult` closure and only
  sends the request inside it (`OpenAIChatAdapter.ts:449-455`, `KoboldCppAdapter.ts:413`, `OllamaAdapter.ts:438`);
  dispatch calls that closure at `:1525` **after** the queue has settled the run and `pump` has freed the lane
  (`llmQueue.ts:347-368`). `runQueuedLLMCall.ts:86` reads the stream inside `execute`, so only side calls
  (summaries, titles, fields) and preflight are serialised today. Streamed session replies are not. The owner's
  ruling on what to do about it is ★P2-b — **this brief is updated with it before the lane starts**; do not begin
  without that paragraph.
- **[C8] Re-entry set leaks across runs.** `pump` builds a run's held-lane set from the async context *pump* runs in
  (`:344`), and pump is called from the previous run's `.finally` (`:347-349`) and the force-detach timer (`:432`), so
  an unrelated next item inherits the previous run's set. Fix: capture `activeLanes.getStore()` at **`enqueue`**,
  keep it on the `Run`, and have `pump`/`runIt` run under that set, never their own context. Inline only for a lane
  the chain already holds. First check whether any nested enqueue still exists in production code (the cited origin
  was the assistant tool-calling turn; Assistant Chat is deprecated — memory `feedback_assistant_chat_deprecated`).
  If none: pin that with a test and drop the cross-lane deadlock case. If one does: enforce a fixed lane order
  (sort keys; a chain may only enqueue on a lane that sorts after every lane it holds, else inline) rather than the
  cycle check first drafted below.

## ★P2-b and the pool controls (owner rulings, 2026-11-13) — this replaces the "do not begin" hold above

1. **A streamed reply holds its host lane for the whole stream.** In `dispatch.ts`, the queued item's `execute` must
   read the stream to its end (as `runQueuedLLMCall.ts:68-92` already does) — the chunk forwarding to
   `request.onChunk` and the accumulation at `:1525-1540` move inside `execute`, so the lane is released when the
   stream ends, is aborted or fails. Status `generating` now spans the stream. Cancel (`onCancel` → `adapter.abort()`)
   must still stop a stream mid-way. This is the main reply path: test it with the fake adapter in `dispatch*.test.ts`
   (a streamed call on a width-1 lane blocks a second queued call until the first stream ends; an abort frees the lane).
   `dispatch.ts` is a peer-released file; edit only the enqueue block and the stream-reading block it now encloses.
2. **Admin controls over the pools — per host, in Admin → Connections.** A new small table (name per §24/§10; grep
   first — candidates "host pool", "lane width"; one row per host key `(scheme, host, port)`, columns: the key, the
   override width, timestamps), owned by the connections module. The queue reads width as: override if a row exists,
   else the derived default (1 local/managed, 4 known cloud). Admin → Connections gains one card listing every host in
   use (derived from the connections table's base URLs + managed adapters), each with its default and an override
   field (1–16), and **one sentence of purpose** (P4): e.g. "How many requests this server takes at once; one for a
   local model, more for a cloud provider." Members never see it (admin shell only). Socket events under the existing
   connections family (one domain context, no new toasts in views). Migration: **`0159`**, generated by this lane
   **only after perf-K's report exists** (K generates `0158`); edit `schema.ts` only then, and append nothing else.
   Second-boot test as for every migration. Docs: `docs/connections.md` one paragraph under an admin heading.
   This is the first piece of the Servers direction (`project_model_lane_lifecycle`): it governs *requests in flight
   per host*, never model residency or loading order — write that line into the card's doc comment.

## What to build

1. `getConcurrencyKey(item)` (`utils/llmQueue.ts:160`) returns the host lane key. The item (`LLMQueueItemInput`,
   `:13-38`) today carries only `connectionName`; both enqueue callers must pass what the key needs:
   `pipelines/runtime/dispatch.ts:1429` and `utils/runQueuedLLMCall.ts:58` (whose own callers are
   `summarizer/index.ts`, `graphBuilder.ts`, `pipelines/runtime/dispatchStep.ts` — they already hold the adapter or
   connection; thread the connection's `id`, `type` and `baseUrl` through, nothing more). The stale comment at
   `:157-159` ("nothing else in this module or its callers needs to change") is corrected.
2. Which hosts are "known cloud": derive from what already exists — the API presets / connection defaults in
   `src/lib/shared/utils/connectionDefaults.ts` and `src/lib/shared/connections/credentials.ts` list the cloud base
   URLs. Reuse that list; do not write a second one (R1). A host not in it, and every managed connection type
   (`*ManagedAdapter`), is width 1. Localhost / loopback / RFC1918 / `.local` is width 1 regardless of the list.
3. `MAX_QUEUE_DEPTH` becomes per lane (same number, per lane).
4. **Re-entry guard (the [C1] hole; superseded by [C8] above where they differ).** `enqueue` (`:219-228`) runs inline when the *current* lane is held by the
   caller's chain. With several lanes: run A holds lane X and enqueues on Y; Y's running item holds Y and enqueues on
   X → both wait forever. Rule to implement: the `activeLanes` store carries **every** lane the causal chain holds;
   a nested enqueue from an active run on a lane the chain does not hold still queues, but the item it queues
   records the chain's held lanes, and a lane never runs an item whose chain holds a lane that is itself waiting on
   this lane (cycle check), in which case it runs inline instead. Write the deadlock as a test first (two lanes, two
   nested enqueues each way) and make it pass; then a starvation test (interactive priority on lane X is not blocked
   by routine items on lane Y).
5. Width > 1: a lane runs up to `width` items at once; the snapshot (`snapshot()`), the status listeners and the
   cancel path (`CancelledError`, `ForceDetachedError`, `onCancel`) must all keep working with more than one running
   item per lane. The admin queue view reads the snapshot — check what it renders (`grep -rn "llmQueue.snapshot\|LLMQueueSnapshotItem" src/lib`)
   and keep its shape; if more than one item can be `running` per lane, the view must not assume one.
6. `docs/connections.md`: one paragraph — calls to different hosts run side by side; a local or managed server takes
   one at a time; a cloud provider up to four; nothing to configure.

## Rules you quote into every worker brief

- P1: the lane key is a pure function of the connection's base URL and type. Same connection, same lane, every
  time. No time-based or load-based choice.
- P3: no setting. P5: nothing user-facing is declared.
- NOMENCLATURE §1 R1–R6, §10 (Connections vocabulary — "lane" is used by channels too (`channels/lanes.ts`); the
  queue's word today is also "lane"; keep "LLM lane"/"queue lane" qualified (R3) and do not introduce a third word),
  §24, and append the new names (the key type, the width constant) to §25 in the same change.
- Managed connections: the supervisor (`managed/supervisor.ts`) already serialises `start()`; the queue's width 1 for
  managed hosts is the only guard against two generations on one GPU — do not loosen it.
- No `crypto.randomUUID` (the queue uses `uuidv4` already).
