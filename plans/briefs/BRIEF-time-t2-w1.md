## Goal

Every lorebook entry (every entry type except History; cast members are not entry rows) gains two properties:

- **Beginning** — the entry's own date parts `year`, `month`, `day` in its `fields` jsonb, exactly as a history entry
  stores its date. No date = *Perpetual*; a date = *Began at ‹date›* (the entry is not read at a moment before it).
  No new column.
- **Decay** — one number, the new column `lorebook_entries.decay_rate` (`real`, NOT NULL, default 0; wire
  `decayRate`). 0 = *Fact*; above 0 and at most 1 = *Living* at that rate. **Nothing reads it for recall**: it is
  stored, validated, sent on the wire, and that's all.

The column and migration `drizzle/0162_entry_decay.sql` are ALREADY generated by the supervisor
(`schema.ts` `decayRate: real("decay_rate").notNull().default(0)`). Do not touch `schema.ts`, `drizzle/**`, or run
`drizzle-kit`.

## Build

### 1. Shared helpers (`shared/lorebooks/amendments.ts`)

- `clampDecayRate(n: number): number` — into [0, 1].
- `decayRateProblem(value: unknown): string | null` — null for a finite number; else the sentence
  🚧 *Decay is a number from 0 to 1.*
- `"decayRate"` joins `NEVER_AMENDED` (the resolver never reads it from an overlay), and
  `amendmentDecayProblem(fields): string | null` — when `fields` has own key `decayRate`, the sentence
  🚧 *A dated change can't change an entry's decay: the decay is part of the entry, so changing it means changing
  the entry itself.* Check every other user of `NEVER_AMENDED` still behaves (grep it, client included; report
  any you could not keep unchanged).
- An exported type for the wire, e.g. `interface EntryTimeWire { decayRate: number; year?: number | null; month?:
  number | null; day?: number | null }`. (`EntryColumns` lives in `shared/entries/types.ts`, which this lane does not
  own; the supervisor queues moving it there.)

### 2. Storage path (`utils/lorebookEntries.ts`)

- `takesBeginning(typeId): boolean` — true when the type declares none of `ENTRY_DATE_PARTS` (so History is false).
- `entryInsert`: for a type that takes a beginning, copy `year`/`month`/`day` from the input when they are numbers
  (absent/null → not stored); `decayRate: clampDecayRate(Number(input.decayRate))` when it is a finite number, else 0.
- `splitUpdate`: for such a type, a payload's `year`/`month`/`day` go to the `fields` half (null clears); a
  payload's `decayRate` (any type) goes to `columns.decayRate`, clamped. Keep the doc comment true (it says a
  `year` sent to world lore is ignored — rewrite that rule).
- `toEntryRow`: every row gets `decayRate: row.decayRate ?? 0`; a type that takes a beginning also gets
  `year`/`month`/`day` (the stored number, else `null`). History's output is unchanged.
- A validator, e.g. `beginningProblem(parts): string | null`, for a payload that names any date part of a type that
  takes a beginning, judged on the merged result (payload over stored): all three null/absent → fine (Perpetual);
  else year must be an integer, month null or an integer ≥ 1, day null or an integer ≥ 1, and a day needs a month.
  Sentences 🚧: *A beginning needs a year.* · *A beginning's year, month and day are whole numbers, and the month
  and day start at 1.* · *A beginning with a day needs a month too.*

### 3. `sockets/entries.ts` (create and the person's save)

- `decayRate` on create or update: refuse with `decayRateProblem` when present and not a finite number; otherwise it
  is clamped by the storage path. History entries accept it too (one number on every entry).
- A type that takes a beginning, on create with a year, or on update that moves its date to a non-null date
  different from the stored one (compare day-wise with `compareDates`/`dayOnly`, as the history path does):
  1. refuse with `TIMELINE_OFF_SENTENCES.dated` when the lorebook's Timeline is off (`timelineOfBook`); clearing
     to Perpetual (all null) is always allowed;
  2. `beginningProblem`;
  3. inside the existing `db.transaction` + `lockBookCalendar`: `assertDateLands`; on update also
     `assertRedateKeepsLines`; and (§4 of the plan) refuse when the entry already has a dated change (an
     `entry_amendments` row of this entry, any line, `base IS NULL`, with a year) dated before the new Beginning:
     🚧 *This entry has a change dated ‹change date›, so it can't begin later, at ‹beginning›. Move or delete that
     change first.*
  4. **never** `assertHistoryDateFree` / `historyEntryOfDate`: those stay History's (`roles.order`). A Beginning on
     a day a history entry holds is accepted, and two entries may begin on one day.
- Date words in sentences: use whatever the existing refusals use for a story date in the book's calendar (look at
  `historyDayOwnerRefusal` / `assertHistoryDateFree`'s sentence) — never invent a second formatter.
- Session writes (`params.sessionId`) are unchanged.
- Inside `db.transaction(async (tx) => …)` use only `tx`.

### 4. `sockets/amendments.ts` (refusals only)

- `cleanFields`: refuse `amendmentDecayProblem` like the date sentence, before anything is dropped.
- Every path that writes or moves an entry amendment's date: when the entry takes a beginning and has one, refuse a
  date before it (day-wise, `compareDates`; on the Beginning's own day is allowed; an undated amendment is not
  judged): 🚧 *This entry began at ‹beginning›, so a change can't be dated ‹change date›, before it. Date the change
  at or after ‹beginning›.* Run the check inside the write's transaction, after `lockBookCalendar`, using `tx`.
  History entries: unchanged.

### 5. `lorebooks/timeline.ts`

- `timelineCountsOf` gains `beginnings`: the number of non-history entries of the book whose `fields` hold a numeric
  `year`. `holdsSomethingDated` is true when there is any. Add `beginnings: number` to `timelineCounts` in
  `shared/sockets/types.ts` (a client worker will show it on the Timeline card).

### 6. Wire types (`shared/sockets/types.ts`)

`Entries.List` / `Create` / `Update` responses carry `LorebookEntry & EntryTimeWire`; `Create`/`Update` params
accept `Partial<EntryTimeWire>`. Keep everything else unchanged.
