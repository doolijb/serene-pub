- **Log search, `channels` needs `reads: ['messages']`** — that a declared channel's rows are the `messages` section, so a widget that declares `channels` must also read `messages` or receive nothing, is said only in the harness's `reads` JSDoc. `widget()` does not warn. — *S: `widget()` adds `messages` to `reads` when `channels` is declared, or refuses the declaration with a sentence.*
- **Log search, the cursor** — `messages` params are `{ channel?, cursor?, limit? }` and the result `{ rows, nextCursor? }`; nothing says what the FIRST page is (no cursor = "older than what you were sent"? or "the newest page"?). I guessed "no cursor = the page just older than the live lines". Then read core's answer (`src/lib/client/components/sessionPage/requests/messages.ts`): core **ignores `channel`, `cursor` and `limit`** and answers "the page's next older page" of its one window. So the example's paging is correct against the harness and against the contract's words, and not what the app does: two widgets paging would steal each other's pages, and a channel-scoped widget gets other lanes' rows. — *M (touches the request table, so needs a ruling per Q4): core honours `channel`/`cursor`/`limit`, or the contract says plainly that `messages` is "the page's next older page" and drops the params.*
- **Log search, saved state** — `ctx.state` is `unknown` and "handed back once on mount" — but it arrives as a push AFTER mount, so reading it in `<script>` gets `undefined`. Needed a `$effect` with a once-only flag and a cast to `{ query?: unknown }`. Every widget with view state will write this. — *S: `ctx.state` present before the component's first render (the host posts it before `ready` resolves), and/or a typed helper `restoreState<T>(ctx, guard)`; say the timing in the guide either way.*
- **Mood dial, the viewer's persona** — the task "the slots of the viewer's persona" has no direct path: `viewer` has only `userId`; `attendance` gives `personaRefs: character:<id>`; `SessionStateOwnerV1` (a `session_cast` owner) carries `key`, `id` (the session_cast row) and `label`, but no `characterId`/`ref`. I declared a third scope (`persona`) and matched the owner by `label === persona.name` — fragile (two members with one nickname). — *M: give a cast owner `ref: character:<id>` (the `characters.v1` grammar), so persona → owner is a lookup, not a name match.*
- **Mood dial, configs** — `owner.configs[slotId]` is `Record<string, unknown>` though the SDK exports `SlotConfig` (`min`, `max`, `of`, …); cast `as SlotConfig` to read a bar's bounds. — *S: type `configs` as `Record<string, SlotConfig>`.*
- **Mood dial, three keys per slot** — a slot has `slotId` (what a write names), `key` (what a person reads) and `qualifiedKey` (what `resolved` is filed under). The JSDoc is right on each, but nothing in the guide says which to use for which; I read the type file three times. — *S: one sentence + a 4-line example in guides/widgets.md §Extra data under `session:state`.*
- **Mood dial, loading has two shapes** — "section absent" and "section present with `loaded: false`" both mean loading; the guide's three-state snippet shows only the first. — *S: add `|| !section.loaded` to the guide's snippet.*
- **Mood dial, settings are untyped** — `ctx.settings` is `WidgetPayload`; my declaration says `step: { type: 'integer', default: 1 }`, but the component reads `unknown` and does `Number(ctx.settings?.step ?? 1) || 1`. — *M: the SDK already infers values from a schema (`SettingsValues<M>`, settings.ts), but `widget()` returns a plain `WidgetDecl`, erasing the literal schema; keep it generic (`WidgetDecl<S>`) and offer `settingsOf(decl, ctx)` typed off it.*
- **Mood dial, pressing by identity** — the guide's table says `invoke(key)` "presses an action by its key"; the deprecation note that a bare key is ambiguous across specs lives on `WidgetVerbs.action`. `WidgetAction` has no `identity` field; I found the `actionIdentity()` helper only by grepping `sdk/src/identity.ts`. — *S: an `identity` field on `WidgetAction` (or name `actionIdentity` in the guide's `invoke` row).*
- **Mood dial, the write params** — the type (`owner: { kind, id }`, `slotId`, `value`) was enough once found, but the natural first try is passing the owner object you already hold (`owner`), which also has `kind` and `id` and so type-checks — and then sends `configs`/`label` over the wire. Core's `slotWriter.svelte.ts` strips it by hand. — *S: say "pass `{ kind, id }`, not the owner row" in the request's JSDoc, or accept the row.*
- **Mood dial, testing the refusal** — a widget that does what the docs ask (hide the button without the write grant) leaves the harness no way to show the ask being REFUSED: there is no button to press. I tested the hidden button through the harness, and the refusal itself with `widgetRequestRefusal(...)` against the declaration's scopes. — *S: `view.ask(kind, params)` on the harness, which asks as the box (asker table + press gate), for exactly this test.*
- **Harness on a stale dist, silently** — the harness bundles the worker side from `sdk/dist`. Against today's dist, `ctx.scope` is missing (loud: "raw.scope is not a function"), but write grants are **silently dropped** by the old receiver (`granted('session:state:write')` is `false`), so the write test fails as "nothing matches '.plus'" — it reads as a component bug. - **Harness, scopes are optional on the decl** — `moodDial.scopes` is `WidgetScope[] | undefined`, so `grants: moodDial.scopes` needs a cast to filter. `reads: decl.reads` works because `reads` is optional too. — *S: `mountComponent({ widget: moodDial, grants })` taking `reads`, `channels` and the scope list from the declaration in one go.*
