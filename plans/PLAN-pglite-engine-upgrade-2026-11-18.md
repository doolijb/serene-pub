## Findings that shape the plan
1. There is no attic upgrade page and the attic keeps no flags in `meta.json` (its state is in the database; it runs as a blocking start-up task while requests wait on `appReady`). The page precedent is `db/unopenablePage.ts`, `src/routes/recovery/pages.ts`, `DatabaseState` in `startup/index.ts`. A progress page is new work, and `src/hooks.server.ts` needs a check before `await appReady` (~165) or every request hangs silently.
2. **An updater rollback after the swap strands the person:** `launcher/internal/update/machine.go` restores only the app folder; the older app then meets a Postgres 18 directory and its recovery restores only `backups/*.tgz`. So the conversion writes a Postgres 16 archive into `backups/` before the swap (PG2).
3. `drizzle(dbPath)` at `db/index.ts:380` opens the directory synchronously at module scope: detection is a synchronous `PG_VERSION` read above it.
4. Open-failure classification is engine-specific (`isPgliteOpenAbort`, `db/errors.ts:131`, wants a `RuntimeError` from `_pg_initdb`; 0.5.x raises `Error("PGlite failed to initialize properly")`): unchanged, the unopenable page never appears on the new engine.
5. Android and Docker builds also ship (`scripts/build-android.js`, `docker.yml`).

## 2. The conversion at start-up
**Engine first, then the attic** (the conversion is schema-blind: it carries a 0.5.3 database at migration 0093, or a half-restored attic, as it stands; migrations and the attic then run on the new engine as today).
**Boot (`db/index.ts`):** after `await acquireDatabaseLock()`, read `PG_VERSION` synchronously: `18` or missing → today's path; `16` → `db` is a stub that throws a named error, no engine constructed; anything else → refusal page. `initialiseDatabase()` runs the conversion, assigns `db` as `reopenDatabase` does, then `runInitialisation()` unchanged. No top-level await. Health stays `starting`. Failure is a new `DatabaseState` variant and page linking to `/recovery`.
**Children** (the parent's heartbeat keeps the lease; pg_dump is synchronous, so the work cannot run in-process). Each is `process.execPath` with its script on stdin and entry URLs resolved by the parent as `resolvePgliteEntry` does; children never write `meta.json` and only hold copies; the parent forwards SIGTERM and waits. **export** (old engine: pages, sequences, ledger, counts, hashes, catalog) · **schema** (old engine + tools: in-memory clone, pre-data and post-data; its own process so the clone does not stack on the export) · **restore** (new engine: fresh target, the two header rewrites, split statements, COPY per table transaction, `setval`, post-data, `RESET ALL`, `ANALYZE`, verification queries, close) · **probe** (new engine: reopens the closed target and reads `RESTORE_PROBE_TABLES`).
**Dependencies:** aliases `pglite-pg16`, `pglite-tools-pg16`; about 14 MB after pruning for the old engine (tools unmeasured); prune rule 17 (hard-coded to `@electric-sql/pglite/dist`) must also cover the alias folder; the licence gate reads each folder's own package.json (confirm the tools package).
**Working folder:** `serene-pub.db.converting-<id>/{source,export,target}` inside the data folder (same filesystem for the swap); reflink where offered.
**Verification gate, all required:** zero statement errors and every page's row count; table set, per-table row counts and row hash; sequences (`last_value`, `is_called`) and ledger (count + hash); catalog lists for indexes, columns, constraints (excluding `contype = 'n'`), enums, views, triggers, extensions, functions, sequence owners; database `postgres`, major 18, UTF8; clean close, then the probe child succeeds. Per-column hashes only to diagnose a failure.
**Seal and swap:** the engine never fsyncs, so the parent fsyncs every file in the target; flag `swap`; rename `serene-pub.db` → `serene-pub.db.pg16-<stamp>`; rename target → `serene-pub.db`; fsync the data folder; flag `done`; delete the working folder. Retry renames on Windows `EBUSY` / `EPERM`.
**Rerun and failure:** a boot that finds any stage before `swap` deletes the working folder and starts from preflight; `swap` alone resumes, decided from what is on disk. On failure: delete the working folder, record `failure`, show the page; the original is untouched.
**Preflight:** disk — refuse below 4× the directory size; recheck once the export reports text bytes. Memory — the smaller of `os.totalmem()` and `process.constrainedMemory()`; starting rule: refuse below max(2 GB, 1 GB + 3× the directory); lower it with the schema child split, 1 MiB pages, hashes after data; re-measure in pg-2.
**WAL:** pg-2 measures `SHOW max_wal_size`, `SHOW wal_recycle`, `pg_control_checkpoint()` and `pg_ls_waldir()` before and after `CHECKPOINT`, the `postgresqlconf` option at initdb, and `wal_level=minimal` with TRUNCATE + COPY in one transaction. Never delete segments by hand. Soak: 200k mixed writes on a disk instance, sampling `pg_wal`, asserting a plateau; if it does not plateau the app must checkpoint itself, which makes it a release gate for pg-1b too.

## 3. Backups and restore
`inspectArchive` returns the engine (the `PG_VERSION` content, inside the megabyte already read); other than 16 or 18 is refused in words. Restoring a 16 archive: `extractTarGz` into `source`, the same conversion from `export`, then `restoreBackup`'s two renames; the seam is `convertDirectory({ source, target })`. `scripts/db-recover.entry.ts` uses the same function. `applyCompanionMeta` must not carry `engineConversion` over. New backups need no change. Old archives stay restorable only while the old engine ships.

## 4. Tests
