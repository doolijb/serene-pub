# REPORT gs-3b (2026-11-17): a guest can play a card someone shared with them (owner rulings G3, C1)

Guest's side only. No migration, no SDK change, no new event. The supervisor ran a scope review (nothing blocking; three notes fixed).

**What a guest sees.** With *Guests can bring their own characters* on, both the **Add a character** and **Add a persona** pickers end with a group **Shared with you** (rows *From ‹owner›*, a help line). A pick adds a pending row to the guest's AI group or their own Personas group, with **Remove**. The session owner's pickers still hide shared cards.

**The copy.** Save sends `sessions:update { sharedCardSeats: [{ characterId, kind }] }` (runs once; never compared with existing seats). Per pick, in one transaction, `copySharedCard` (`server/cast/sharedCardCopy.ts`) makes a **new** cast member with no card in **the session's notes**, carrying the card's words, sprites, gallery, card sheets and faces (a base version on the card's version, then `makeMemberCardless` with the new cause `shared`); no link back (`character_id` null, no parent version); files belong to the notes' owner. Edits never cross in either direction (tested).

**The seat.** By member only; the shared card is never written into `character_id` / `persona_id`. Persona picker → a card-less player seat played by the guest, named as the card. Character picker → a card-less character seat seated by the guest. Same checks as an own card first (the share, the switch, the genre's seat kind).

**Who can do what.** The guest: changes the seat's sheet in play under today's hand-edit rule; renames or removes a player seat; cannot edit the member's words, art or lorebook sheet. The session's owner: everything. The sharer: no change, no notification, no reach.

**When the guest is removed.** A player-seat copy is benched, still the guest's (the owner takes it back with **Played by**); a character-seat copy goes to the owner; both members stay in the notes.

**The linked path is closed.** `verifyBindingTargetAccess` links a card only if the caller owns it or sees it through a seat in a session they are in; a share alone is not enough (four callers, forged-request tests).

**Tests.** Server: `sessions.sharedCardSeat.int` 13/13, `sharedCardLinkedBinding.int` 6/6; existing guest-seat, cast-to-take, handover, seating 52/52. Client: `editSessionSharedCards.dom` 6/6; eight DOM files 93/93. `tsc`, `npm run check`: 0 errors in lane files.

**Outside Files owned.** `server/utils/sessionAccess.ts`: `canViewCharacterThroughSessions` split out of `canViewCharacter`, no behaviour change. `docs/sessions.md`: first bullet of "What guests may seat".

**★ New words (alt):** field `sharedCardSeats` (`sharedCardCopies`); `copySharedCard` / `sharedCardRefusal` (`castCopyOfSharedCard`); cause `shared` (`share-copy`); refusal *Only a character someone shared with you can be copied into a session.* (*That character isn't shared with you.*); help *Picking one puts a copy in this session; the original stays as it is.* (*A copy joins this session; the original never changes.*); screen-reader names *Shared characters*, *Shared cards to add*.
